## 1. Project Overview

DesktopDashboards is a lightweight Windows desktop gadget app. It keeps
multiple arbitrary web apps, AI artifacts (such as Muse Spaces), and
local HTML files resident on the desktop as gadgets — pinned to the very
back / wallpaper layer — instead of living in browser tabs.

- **Repo:** `github.com/DashingMZA/DesktopDashboards`. Default branch
  **`main`**. Owner: Muhammad Zaheer Ahmad (DashingMZA).
- **License:** MIT (`LICENSE`).
- **Stack:** Tauri 2 + vanilla JS (no frontend framework; the frontend
  is a single static `src/index.html`), Rust edition 2024, pnpm 12.19.0,
  Node ≥ 24, `cargo test` (Rust unit tests). No JavaScript test suite:
  no Vitest, no Playwright, no `tests/` directory.
- **Platform:** Windows 10/11 only. Installer: NSIS. Portable ZIP.
  Auto-updater via GitHub releases (`latest.json`).
- **External data:** whatever URLs the user registers as gadgets,
  loaded in embedded WebViews from a dedicated WebView2 profile
  (`%LOCALAPPDATA%\DesktopDashboards\webview`). Login state for a
  service is shared across gadgets. No backend, no database, no
  accounts of its own, no telemetry.
- **Config:** `%APPDATA%\DesktopDashboards\config.json` (atomic writes
  with a one-generation `.bak` fallback).

## 3. Architecture and Directory Map

```text
src/
  index.html                          Manager window UI (single static page)

  src/tray.rs                         System tray menu
  src/widget.rs                       Gadget window management + tests
  src/win32.rs                        Win32 pinning (HWND_BOTTOM / WorkerW,
                                      layered windows) — #[cfg(windows)]
  tauri.conf.json                     Product/bundle metadata, updater,

  SPEC.md                             Feature spec, Draft v0.3 (single

.github/workflows/                    ci.yml, codeql.yml, label.yml, release.yml

                                      ISSUE_TEMPLATE/, FUNDING.yml
```

Data flow: the manager window (`src/index.html`) calls Tauri commands
in `lib.rs` (`list_widgets`, `add_widget`, `toggle_widget`,
`update_widget_settings`, …) → `widget.rs` creates/destroys frameless
WebView gadget windows → `config.rs` persists them to `config.json`.
Gadgets share one WebView2 profile directory, so a login done in one
gadget is available in the others.

## 6. Architecture Decisions and Rationale

- **Tauri 2 over Electron:** smaller binaries, native WebView2.
  Consequence: desktop builds need per-OS CI (release.yml is
  Windows-only) and a signing key for the updater.
- **Vanilla JS frontend, no framework:** the UI is plain HTML/CSS/JS
  in a single file. Consequence: no build step for the frontend
  (`frontendDist: ../src`), no lint/typecheck tooling.
- **Dedicated WebView2 profile:** gadgets share one `user_data_dir`
  so logins persist across gadgets without conflicting with other
  Tauri/WebView2 apps. Consequence: clearing that profile logs the
  user out of every gadget at once.
- **Atomic config writes:** `config.json` is written via
  `.tmp` + flush + rename, with a one-generation `.bak` fallback.
  Consequence: a crash mid-save cannot corrupt the gadget list.
- **Win32 pinning (Mode A / Mode B):** Mode A pins gadgets to
  `HWND_BOTTOM`; Mode B embeds them in the `WorkerW` wallpaper layer
  so they survive `Win + D`. Consequence: this code is
  `#[cfg(windows)]` and cannot be exercised on Linux CI — only
  `cargo test` (pure logic) runs there.
- **pnpm 12.19.0 + node ≥ 24:** owner's standard toolchain across repos.

## 10. Failed Attempts and Lessons Learned

- **GitHub App cannot push workflow files.** A push containing
  `.github/workflows/*.yml` fails with 403 on git/trees (App lacks
  workflows permission). Workflow files go via the owner's web-UI
  upload; verify byte-identical afterwards.
- **Background work must not depend on /tmp.** A VM replacement
  wipes /tmp and kills background processes: the v0.1.1 release
  monitor and the local `cargo test` both died that way on
  2026-11-17. Keep monitor scripts under `~/workspace/scripts/` and
  their logs under `~/workspace/`, never /tmp.
- **GitHub's get-release-by-tag 404s for DRAFT releases.** To check a
  draft, list releases (`GET /releases`) and filter by tag instead.
- **GitHub job-log downloads 302 twice** (API → signed Azure blob
  URL, sometimes via a second hop). Do NOT forward the GitHub auth
  header to the blob host (401); follow redirects manually without
  auth. The download may be plain text, not a zip — check the first
  bytes before unzipping.
- **GitHub push-files is UTF-8 TEXT ONLY.** Binary files (PNG
  screenshots) cannot be pushed via the connector — binary assets go
  via the GitHub web UI upload; do NOT work around with PATs.
- **Never claim a Rust fix is compile-verified in the sandbox
  without running it.** Cargo 1.100.0 is installed here now (rustup,
  2026-11-16/17), so `cargo test` CAN run locally — but it compiles
  the full GTK stack first (slow) and the app itself is Windows-only,
  so CI remains the authority for the release build.
- **Copied docs lie.** The docs set copied from another project named
  the wrong app, the wrong scripts, the wrong files, and a SPEC
  section that does not exist. Verify every doc claim against the
  repo it lives in.

## 12. Security and Operational Considerations

- Signing key: lives in GitHub repo Secrets, never in the repo. Key
  files (`DesktopDashboards.key`, `DesktopDashboards.key.pub`) are
  gitignored. No secret values are recorded in this file.
- Updater trust: `tauri.conf.json` embeds a minisign public key and
  the releases endpoint — rotating the key requires coordinated config
  + secret updates.
- Capabilities: `src-tauri/capabilities/default.json` (manager window)
  and `widgets.json` (gadget windows) grant only what the app needs —
  keep grants minimal when touching them.
- No backend, no accounts, no telemetry. Gadgets load user-chosen
  URLs in their own WebViews; same-origin navigation stays inside a
  gadget, external links open in the OS default browser.
- Config and WebView profile live under the user's own
  `%APPDATA%` / `%LOCALAPPDATA%` — no data leaves the machine except
  the gadget pages themselves.
